The Programming subsystem consolidates the entire software intelligence of the UGV, encompassing high-speed autonomous navigation, airfield SLAM mapping, global/local path trajectory planning, multi-robot coordination, and secure UAV-to-UGV command and control (C2) datalinks.

💻
Onboard UGV Compute Implementation: Hilbert's Laptop & STM32 F446RE

The primary UGV onboard computer is Hilbert's Laptop, running Ubuntu 24.04 LTS with ROS 2 Jazzy. It connects via USB to an STM32 F446RE microcontroller, which executes real-time motor control loops and bridges command velocity (cmd_vel) instructions to the ZLAC8015D servo driver to drive the UGV hub motors. This architecture was adopted due to capstone budget limitations precluding the purchase of a new NVIDIA Jetson platform, while all available Jetson developer kits within the NUS Engineering Design and Innovation Centre (EDIC) are currently committed to CDE3301.

🤖 4.3.1 ROS 2 Distribution Evaluation & Selection

Robot Operating System 2 (ROS 2) serves as the core computational middleware for the runway Foreign Object Debris (FOD) inspection UGV. ROS 2 provides an industrial-grade Data Distribution Service (DDS) abstraction layer, real-time deterministic executors, lifecycle node management, and an extensive ecosystem of production autonomy libraries (Nav2, SLAM Toolbox, and robot_localization). A comparative evaluation across consecutive modern distributions—ordered from latest to oldest—was conducted to determine the optimal software platform for multi-year capstone longevity and hardware integration.

🎯 Engineering Justification for ROS 2 Jazzy Jalisco

ROS 2 Jazzy Jalisco on Ubuntu 24.04 LTS was chosen as the operational baseline because its 5-year support window (active until May 2029) guarantees software maintenance beyond the capstone delivery timeline.

  • Native OS & Compute Acceleration Parity: Jazzy aligns natively with Ubuntu 24.04 LTS running across both developer laptops (WSL2) and the onboard NVIDIA Jetson AGX Orin running JetPack 7.x. This eliminates Docker virtualization overhead, allowing direct bare-metal access to CUDA, TensorRT, and hardware communication ports (/dev/ttyACM0 for STM32 micro-ROS).
  • Mature Simulation & Safety Interlocks: Jazzy provides native integration with modern Gazebo Sim (Harmonic / GZ 8.x) via ros_gz_bridge alongside modern Nav2 algorithmic features—notably dynamic nav2_collision_monitor safety polygons and Smac smooth path planning out-of-the-box.
  • Driver Ecosystem Availability: Crucial hardware packages (including rplidar_ros, nmea_navsat_driver, robot_localization, and micro_ros_agent) offer verified, stable builds under Jazzy without the dependency breaks or source compilation overhead present in Lyrical Luth.

Why Gazebo Harmonic Over NVIDIA Isaac Sim?

While NVIDIA Isaac Sim provides unmatched photorealism and GPU-accelerated synthetic training data, it imposes strict hardware prerequisites (dedicated desktop NVIDIA RTX 3070+ GPUs with 8–12 GB VRAM) and a >50 GB software footprint. In contrast, Gazebo Harmonic runs fluidly on standard student and developer laptop workstations, has zero proprietary licensing restrictions, and integrates natively with ROS 2 Jazzy without fragile bridge layers.

Phase 1 Simulation Architecture Workflow

URDF / Xacro model of the UGV (differential drive, wheel base, caster wheel, LiDAR & camera transforms) → Spawned into Gazebo Harmonic with simulated runway world → ros_gz_bridge maps /cmd_vel, /odom, /scan, and /tf → Nav2 & SLAM Toolbox execute in ROS 2 Jazzy → Visualized in RViz2.

Simulation Robot Model: AgileX Scout V2 (Proxy Platform)

The Phase 1 Gazebo simulation uses the publicly available AgileX Scout V2 URDF/Xacro model as a proxy platform (a 4WD skid-steer chassis modeled via differential-drive kinematics), since the custom FOD Hunter UGV CAD and URDF model is currently being finalized. The AgileX Scout V2 provides comparable kinematic control behavior (commanded via geometry_msgs/msg/Twist with linear $x$ and angular $z$), LiDAR mounting elevation, and wheelbase footprint to our intended physical UGV platform, making it a robust placeholder for Nav2 path planning, costmap inflation, and obstacle avoidance tuning.

🧭 4.3.3 Autonomous Navigation, SLAM & Path Planning Architecture

The UGV autonomous navigation framework runs under ROS 2 Jazzy on Ubuntu 24.04 LTS, fusing 2D/3D LiDAR, IMU orientation, and wheel encoder odometry from the STM32 F446RE into the Nav2 stack. The system is engineered to navigate straight runway corridors and turnaround loops at speeds up to $\ge 10\text{ km/h}$ ($2.78\text{ m/s}$) while executing dynamic obstacle clearance.

1. Mapping Methods & SLAM Algorithm Comparison

Runways present severe SLAM challenges: wide 60-meter expanses lack dense vertical geometric landmarks, causing standard scan-matching algorithms to suffer severe longitudinal slip and pose covariance explosion. Four SLAM candidates were rigorously compared:

SLAM Algorithm Core Mathematical Formulation CPU Overhead Memory Scalability (5 km Strip) Loop Closure Capability Selection Status
SLAM Toolbox Pose Graph Optimization (Karto SLAM derivative with Ceres Solver) Low – Moderate Linear $O(N)$ with Submap Serialization Multi-threaded, high-speed loop closures; supports lifelong and localized incremental updates. SELECTED (Phase 1 & 2)
Google Cartographer 2D/3D Submap Graph SLAM with Branch-and-Bound scan matcher High (Heavy CPU Spikes) Moderate (Caches full probability grids) Robust global loop closures, but can freeze low-power edge nodes during real-time map building. REJECTED (High Latency)
Gmapping Rao-Blackwellized Particle Filter (RBPF) Moderate (Expands with particles) Exponential $O(K \cdot N)$ Memory Growth Suffers particle depletion over long corridor strips; lacks lifelong serialization. REJECTED (Particle Depletion)
Hector SLAM Gauss-Newton Scan Matching (pure odometry-free) Very Low Low Zero loop closure capability; severe longitudinal drift in featureless airfield environments. REJECTED (No Loop Closure)
Decision Justification (Mapping): SLAM Toolbox was selected due to its asynchronous thread decoupling, efficient submap serialization (allowing 5 km runway maps to load instantly without re-processing entire graphs), lifelong map merging, and minimal CPU footprint on Hilbert's Laptop.

2. Global Path Planning Algorithm Comparison

The global planner computes an obstacle-free route from the UGV's current position to the coordinates cued by the aerial UAV scout. It must generate kinematically feasible trajectories over hundreds of meters in minimal compute time.

Smac Planner 2D (A*) Cost-aware A* with Dubins / Reeds-Shepp heuristic options Holonomic / Non-holonomic compatible < 8 ms (Near Instantaneous) Optimal: Highly efficient straight-line corridor generation down runway tarmac. SELECTED (Corridor Sprints)

3. Local Planner & Trajectory Controller Comparison

The local controller runs at 20 Hz, translating the global path into linear velocity ($v$) and angular velocity ($\omega$) commands sent to the STM32 F446RE. Operating at speeds $\ge 10\text{ km/h}$ ($2.78\text{ m/s}$) demands exceptional high-speed tracking stability without lateral oscillations.

Local Controller Control Philosophy High-Speed Stability (≥10 km/h) Compute Latency (per cycle) Curvature Velocity Regulation Selection Status
Regulated Pure Pursuit (RPP) Geometric lookahead tracking with adaptive curvature braking & collision checks Outstanding (Zero lateral hunting) < 2 ms (Ultra-Lightweight) Yes • Automatically scales velocity down inversely with path curvature. SELECTED (Primary Controller)
MPPI Controller Model Predictive Path Integral (Vectorized stochastic rollouts) Excellent (Optimal trajectory generation) ∼ 15–25 ms (CPU/GPU bound) Yes • Naturally incorporates dynamic kinematic cost models. BENCHMARKED (Dynamic Obstacle Mode)
DWB (Dynamic Window) Discrete forward simulation over $(v, \omega)$ velocity space with cost critics Prone to severe oscillation at >2.0 m/s ∼ 12 ms No • Relies on heuristic trajectory penalty critics. REJECTED
TEB Local Planner Timed Elastic Band topological optimization Variable latency during fast sweeps > 30 ms (CPU spikes) Partial • Acceleration bound constraints. REJECTED
Decision Justification (Local Control): Regulated Pure Pursuit (RPP) was selected as the operational standard. RPP guarantees smooth, non-oscillatory steering along high-speed straightaways, regulates vehicle speed when executing tight turns to prevent tire slippage, and consumes negligible CPU overhead (<2 ms per 20 Hz control loop), ensuring real-time reliability on Hilbert's Laptop.

4. Nav2 Costmaps & Autonomous Recovery Behaviors

Layered Costmap Pipeline

  • Static Layer: Encodes tarmac runway boundaries and non-traversable grass medians.
  • Obstacle Layer: Real-time 2D/3D LiDAR point-cloud ray-tracing (clearing and marking dynamic airfield obstacles).
  • Inflation Layer: Exponential decay safety buffer matching vehicle footprint (800 mm width) with 0.3 m clearance margin.

Fail-Safe Recovery Behaviors

  • Clear Costmap: Resets transient LiDAR ghost clusters if vehicle detects false entrapment.
  • Back-up Behavior: Reverses 0.8 m along vehicle centerline if forward path is blocked.
  • Spin Behavior: Controlled in-place yaw sweep to re-localize scan matching before re-planning.

Why A* Consistently Wins in This Benchmark: The interactive visualizer canvas is modeled as a runway corridor — an open, obstacle-sparse environment with few walls. This is A*'s ideal use case: its Manhattan/Euclidean heuristic efficiently guides the search directly toward the goal, minimizing unnecessary node expansions. BFS and Dijkstra explore nodes uniformly in all directions (no heuristic), expanding far more cells before reaching the goal. In complex, enclosed environments with dense obstacle arrays, all algorithms would converge to similar exploration counts. The A* advantage here reflects the real-world runway environment our UGV operates in — wide open tarmac with sparse obstacles.

📡 4.3.4 Multi-Agent C2 Communications & Datalink

The communications architecture bridges the aerial UAV scout, ground UGV sweeper, and airfield Base Station. To reconcile military RF restrictions with rapid software prototyping, a two-phase datalink strategy is executed:

Phase 1: Benchtop & Corridor Testing

Private Router & CycloneDDS Unicast (Aerial Companion Computer & UGV Controller)

Operates across a dedicated local Wi-Fi router subnet (192.168.1.0/24) at 5 GHz. The Aerial Companion Computer / Simulated UAV Ground Station (Raspberry Pi 5 / Workstation) communicates with the UGV Main Compute Node / Navigation Controller over ROS 2 Jazzy. Employs Eclipse CycloneDDS with explicit unicast peer discovery configured via the cyclonedds.xml profile using <Peers> elements. This suppresses multicast traffic across subnets that block mDNS/multicast, eliminates network storms, and guarantees deterministic, low-latency (<15 ms) telemetry transfer.

Phase 2: Outdoor Physical Airfield

Microhard P900 V2 Encrypted RF Datalink

Transitions to air-gapped 917–925 MHz Frequency Hopping Spread Spectrum (FHSS) serial transceivers with hardware AES-256 encryption. Delivers robust >5 km Line-of-Sight telemetry across active airfield runways, fully compliant with Singapore IMDA TS SRD standards.

Structured C2 Telemetry Interfaces

To preserve wireless bandwidth and eliminate multi-second video streaming latency, all aerial computer vision inference runs locally at the edge on the UAV. Only compact, structured JSON telemetry packets (< 2 KB) are transmitted across the datalink with 7-decimal-place geodetic precision for centimeter-level RTK alignment:
